# StreamVibe (Frontend)

**StreamVibe** is a TV shows and movies streaming platform with a React/TypeScript frontend, built with care, attention to detail, and the mindset of “let’s do it right from the start.”

The goal here isn’t to reinvent anything: it’s to have a solid, modern foundation that works well. Authentication, email verification, password recovery… **it’s all set up!**

It’s a project that speaks to those who’ve been in the field for a while, but also welcomes those who are starting out and want to understand how to build something clean and scalable.

If you like an organized frontend, clear structure, and code that’s a pleasure to maintain, take a closer look — it was built with that in mind.

---

See the wiki in [react-front-streamvibe.wiki/](https://github.com/BAD-WOLF/react-front-streamvibe/wiki) for architecture, structure, features, setup, and development guide.

## Talking to the API

Every screen uses the StreamVibe API (`VITE_BACKEND_API_DOMAIN` in `.env.development` / `.env.production`). The client lives in `src/shared/api/`:

- `httpClient.ts`: adds the `/{locale}/api` prefix, unwraps the `{success, data, message}` envelope, turns `{success: false, error}` into an `ApiError` (`type`, `message`, `errors`, `actionRequired`) and, on protected routes, sends the JWT and renews it once with the refresh token on a 401 (`POST /{locale}/api/token/refresh`).
- One service per backend module, mirroring the API: `auth.service.ts`, `verifyEmail.service.ts`, `repassword.service.ts`, `movie.service.ts`, `person.service.ts`, `image.service.ts` and `health.service.ts`.
- The response types are in `src/shared/types/` (`payloads/`, `params/` and `responses/` per module).

URLs always start with the locale (`/pt_BR/...`, `/en/...`, `/es/...`), the same prefix as the API. The locale also picks the UI language (catalogs in `translations/`, generated by `yarn i18n:extract`) and the TMDB content language (`language` query parameter).

| Page | Route | API |
|---|---|---|
| Login / register | `/:locale/auth` | `login_check`, `register`, `resend-verification`, `verify/email/status/{userId}` |
| Email confirmation | `/:locale/auth/verify-email?expires&id&signature&token` | `verify/email/validate`, `verify/email` |
| Password reset | `/:locale/auth/repassword/:token?` | `reset-password`, `reset-password/status/{token}`, `reset-password/confirm`, `reset-password/cancel` |
| Account | `/:locale/account` | `reset-password` (own email), `reset-password/requests/{userId}`, `verify/email/status/{userId}` (admin) |
| Home | `/:locale/home` | `movies/trending/{day,week}`, `movies/popular`, `movies/top-rated`, `movies/now-playing`, `movies/{id}/videos` |
| Lists | `/:locale/movies/list/:list` | the four lists above, paginated |
| Search | `/:locale/movies/search?q=` | `movies/search/{query}/{page}` with `year`, `primary_release_year`, `region`, `include_adult` |
| Movie | `/:locale/movies/:id` | details, credits, videos, images, similar, recommendations |
| Person | `/:locale/person/:id` | details, external ids, images, movie credits, TV credits |
| Image viewer | (movie and person galleries) | `images/sizes`, `images/info/{endpoint}`, `image/{size}/{endpoint}`, `image/{endpoint}` |
| Footer | every content page | `GET /health` |

## Strict typing

TypeScript runs in its strictest mode and ESLint asks for a type everywhere, so the IDE flags a missing type while you write the code:

- `tsconfig.app.json`: `strict` plus `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noImplicitReturns`, `noImplicitOverride` and `isolatedDeclarations` (every export has a type that can be read from its own code).
- `eslint.config.js`: `strictTypeChecked` (with type information), plus:
  - `typedef`: every variable, destructuring, parameter and property is annotated. The style objects in `src/shared/styles/ts/` are the one exception, the same one their `// noinspection TypeScriptExplicitMemberType` already makes;
  - `explicit-function-return-type` and `explicit-module-boundary-types`: every function, callbacks included, declares its return type;
  - `strict-boolean-expressions`: a condition is always a boolean (`hasText(value)`, `value !== null`, `items.length > 0`), never a "truthy" string, number or object. The helpers are in `src/shared/utils/guards.ts`;
  - `switch-exhaustiveness-check`: a `switch` over a union or an enum handles every case.

Commands: `yarn typecheck` (tsc), `yarn lint` (ESLint, fails on any warning) and `yarn verify` (both). The **Check** workflow (`.github/workflows/check.yml`) runs the lint and the build on every pull request to `develop` and `master`.

In the IDE:

- **PhpStorm / WebStorm**: *Settings › Languages & Frameworks › JavaScript › Code Quality Tools › ESLint* → **Automatic ESLint configuration**, and *Settings › Languages & Frameworks › TypeScript* → the project's `node_modules/typescript`. Each problem shows up in the editor as you type and in the *Problems* tool window.
- **VS Code**: install the recommended ESLint extension (`.vscode/extensions.json`) and pick *TypeScript: Select TypeScript Version › Use Workspace Version*. The devcontainer already does both.

### Pending on the backend side

- The JWT carries only `username` (email) and `roles`: there is no way to know the logged user's id, which `reset-password/requests/{userId}` needs. The front remembers the `user_id` returned by the registration on that browser. Adding `id` to the JWT payload (or a `GET /me`) would remove that limit.
- CORS does not expose `Retry-After` (`expose_headers` only has `Link`), so the front cannot tell how long to wait after a 429.
- The confirmation email still links to the API (`/verify/email`), which answers JSON. Pointing it to `{FRONT}/{locale}/auth/verify-email?...` makes the confirmation page above the landing page.
- No genre, discover or TV details routes yet: the home rows are the four lists, and TV credits have no link.
